# OpenCode V1 会话性能记录

本轮优化保留 V1 adapter；V2 后续使用独立 adapter，共用 Deck 的会话操作与分页契约。所有测试均使用临时目录、独立端口和合成会话，没有替换运行中的 OpenCode 或操作用户会话。

## 已确认的适配开销

- 打开会话原先下载并归一化全文，再向浏览器返回最近几轮。现在优先使用原生 `limit` / `before` 分页，补读到完整回合边界；旧版接口保留全文回退。
- 模型目录读取不再阻塞正文。后台预取串行读取尾部，搜索索引在交互期间暂缓新工作。
- 菜单分支改走对应 Agent API。删除与分支前后端均防重复提交，跨操作冲突会明确报错。
- 按轮分支优先验证并复用消息边界；冷缓存或版本变化时，从尾部读到所选用户消息即可定位下一条用户消息，不必总是下载全文。选择很早的轮次仍可能需要遍历全部历史。
- 删除确认使用轻量响应；失败保留原会话并允许重试。等待分支时切换会话，完成结果不会覆盖当前导航。

## 隔离测试结果

2026-10-17，OpenCode V1 1.18.34，约 161 条用户消息、10.55 MB 原生历史的合成样本：

| 操作 | 优化前 | 优化后 |
| --- | --- | --- |
| 热打开（adapter 测量中位数） | 约 88 ms | 约 33 ms |
| 打开时原生历史传输量 | 约 10.55 MB | 约 2.11 MB |
| 已读会话按轮分支 | 约 1314 ms | 约 1166 ms |
| 按轮分支的原生响应传输量 | 约 10.55 MB | 约 1.2 KB |
| 删除 | 18–39 ms | 8–18 ms |

以上是隔离样本，不代表实际用户历史或所有机器的端到端延迟。之后补充的冷缓存边界优化由回归测试验证：1000 条用户消息中选择倒数第十条，只读取 32 条尾部消息即可取得正确排除边界；没有将此单元测试视为端到端计时。

## 分支复制事件的额外开销

V1 fork 保留源消息的创建时间，却为分支赋予新的会话创建时间。适配器会对明确早于新会话创建时间、且当前不在运行中的复制消息合并历史通知，避免把旧助手正文再次作为实时输出转发给浏览器。复制停止 250 ms 后发送轻量 `thread/historyUpdated` 通知，已打开的会话按既有机制重新读取尾部。缺失时间戳、正常新消息和正在运行的回合保持原处理；删除、重启、离线会取消待发通知。

1000 条、每条 8 KB 助手正文的合成事件回归验证：不转发正文，最终只有一条不足 300 字节的历史通知；正常新回复继续转发，删除不会留下延迟通知。此结果验证 Deck 到浏览器的重复传输得到消除，并不代表 OpenCode 到 Deck 的 SSE 传输或原生 fork 计时下降。

## 原生 fork 的剩余瓶颈

直接调用原生 API，1000 条、每条约 8 KB 的用户消息：V1 1.18.34 fork 约 5355 ms；临时下载的 V1 1.19.3 约 5517 ms，其删除约 46 ms。该测试绕过 Deck，因此无法仅靠减少 Deck 请求消除这段耗时。

[V1 1.19.3 原生实现](https://github.com/anomalyco/opencode/blob/v1.19.3/packages/opencode/src/session/session.ts#L691) 先读取源会话全部消息，再逐消息生成新 ID、重映射 assistant 的 parentID，逐 part 重映射消息归属与 compaction 边界；每次 `updateMessage` / `updatePart` 都等待事件发布完成，整个复制循环串行执行。源码和计时共同说明：大历史 fork 仍有随消息与 part 数量增长的原生成本；事件发布内部各阶段的占比尚未单独测量。

要使这类原生 fork 进一步接近 Codex，需要在 OpenCode V1 上游探索批量持久化与事件发布，验证 ID/parent/compaction 映射、事件顺序、失败一致性和外部 TUI 可见性。Deck 不直接写 OpenCode 私有数据库，也不以丢弃历史或只复制摘要替代完整分支。

当前尚未证明所有历史体量下分支均达到 Codex 的性能。V2 的接口与事件语义独立，不能作为 V1 的透明替换。
